Anchor

A retrieval system over vLLM's documentation that refuses to answer when it cannot show its work. Every claim is traced to the span it cites; claims that name a CLI flag are checked against vLLM's actual source. The deliverable is not the chatbot — it is the measured curve between how strict the system is and how often it answers at all.

What it is

the thesis, in one page

Most retrieval demos answer a question and cite a source. Anchor does that, then asks a harder question: does the cited source actually say this? Three verifiers answer it, ordered cheapest first.

  • The symbol oracle is exact and free. --max-num-seqs either exists in vLLM's argument parser at a pinned commit or it does not, and no model's opinion changes that. This is what makes a subset of the faithfulness checks ground-truthed rather than judged — unusual for a RAG evaluation project, and only possible because the corpus is code.
  • Span attribution is free but measures similarity, which is a proxy for support rather than support itself.
  • An LLM judge reads claim and span together. It is the only one that catches a claim sitting close to its span while stating a different number.

Answers whose claims cannot be supported are withheld rather than guessed. The threshold that decides this is a config value, and sweeping it produces the curve this project exists to measure.

How it works

seven stages, each with its own CLI command

The numbering here is real: each stage consumes the previous stage's output, and every stage after the first pins itself to the commit the corpus was ingested at.

  1. 01

    Ingest

    Clone vLLM at a pinned commit as a blobless partial clone. Parse docs, README and public docstrings. Every document records its version and commit, which is what later makes staleness detectable.

  2. 02

    Chunk

    Two strategies, both written to the database at once so they can be queried identically: a naive 512-token sliding window, and a structure-aware splitter that never splits a fenced code block.

  3. 03

    Index

    Embed with bge-small-en-v1.5 into pgvector with an HNSW index, and build the Postgres full-text vector in the same row. One datastore for dense and sparse means hybrid search is a single SQL statement.

  4. 04

    Retrieve

    Dense and sparse top-k, fused with Reciprocal Rank Fusion, then reranked by a bge-reranker-base cross-encoder over the shortlist only.

  5. 05

    Generate

    Numbered context spans, with the model required to cite span numbers inline. That requirement is not cosmetic — it is what makes every downstream check possible.

  6. 06

    Ground

    Split the answer into claims, score each against the span it cited, route checkable names to the oracle, and apply the abstention policy.

  7. 07

    Evaluate

    Run the golden set across configurations. Every run writes a row holding its full config and git SHA, so any number can be traced to what produced it.

Data model

Seven tables in Postgres 16 with pgvector. documents and chunks hold the version-tagged corpus; symbols is the oracle; golden_queries, runs, answers and claims hold the evaluation. Cost and latency are recorded on every answer from the first run rather than estimated later.

The corpus finding

where vLLM's documentation actually lives

Retrieval for "what does max_num_seqs do" returned the wrong document, and the cause turned out to be the corpus rather than the ranking. vLLM documents its engine arguments almost entirely as attribute docstrings — a bare string after a field assignment: 

max_num_seqs: int = Field(default=DEFAULT_MAX_NUM_SEQS, ge=1)
"""Maximum number of sequences to be processed in a single iteration."""

Python's ast.get_docstring cannot see these — they belong to no function or class — so the obvious docstring walk drops every one. In vllm/config/ alone that is 532 field descriptions.

Why this compounds

The rendered engine-arguments page is generated from those same fields at docs build time and is not committed. The source tree holds only a stub ending in an mkdocs include directive, and 29 doc pages share that shape. So the authoritative description of every engine flag was missing from both the docs sources and a naive docstring pass.

After capturing them, the top reranked span for that query went from a wrong document to SchedulerConfig.max_num_seqs at 0.99. This is also the clearest argument for the symbol oracle: for flags and config keys, ground truth is in the source tree, not the prose.

Chunking

measured, not judged — 6,245 fenced code blocks

For every fenced code block in the corpus, does some chunk contain its body verbatim? A block split across two chunks fails, because neither half is a command anyone can run.

Aggregate integrity understates the effect; the split by block length is where the real result is.

Reported flat, fixed-size chunking keeps 97.6% of blocks intact and the strategy looks barely worth having. Split by length, it keeps only 31% of blocks over 256 tokens — the multi-line configs and full serve invocations a user actually wants to copy whole.

The mechanism is arithmetic, not mystery. With a 512-token window and 64-token overlap the stride is 448, so a block survives only if its length fits in what remains of the window where it lands. Worst-case alignment leaves 65 tokens.

Measured caveat

11 of 6,245 blocks exceed the encoder's 512-token input limit, the largest at 913. Structure-aware chunking keeps those whole in storage, but bge-small still truncates them at embed time — "intact" means retrievable as text, not fully embedded.

Three things the table supports

  • Sparse alone reaches only 0.25. Not a bug. These are natural-language issue titles that share almost no vocabulary with the docs; keyword search cannot match "concurrent sequences" to max_num_seqs. It earns its place inside the hybrid, not on its own.
  • Reranking helps structure-aware far more than fixed, lifting recall@3 from 0.72 to 0.90 against 0.60 to 0.68. A cross-encoder scores a query against a passage, and a window starting mid-sentence is a worse passage to score. Chunking and reranking are not independent choices.
  • Only two questions are never retrieved by any configuration — the same two, after adding nineteen more. Both were flagged as expected failures during curation, before the harness existed.

The golden set

52 questions, every one filed by a real person on vLLM's issue tracker, harvested from issues labelled usage and documentation and sorted by reaction count. 563 candidates were harvested and curated against retrieval evidence rather than titles.

Nothing is synthesised, and that is the point: a model-generated set is written in the vocabulary of the documentation it came from, so it flatters retrieval and measures the wrong thing. Two curation rules carry the set's integrity: questions the system currently fails are kept, because a set built only from what retrieval already finds is a transcript of current behaviour; and questions no documentation can answer are dropped, not marked hard.

The model must cite a span number after every factual claim. That requirement is load-bearing: it means the (claim, span) pairs the grounding layer needs are already in the text, so claim extraction is deterministic and re-scoring an answer under a different threshold costs nothing.

A retrieval signal hiding in the generation numbers

23% of supplied spans are never cited. That is not a generation fault — rerank_top_n is 5 and answers typically use fewer, so the surplus is paid for in input tokens on every query. The triad later put 41% of spans as not useful, judging independently and without seeing which were cited. Two unrelated measurements agreeing is much stronger than either alone.

Two ways it was wrong before it was right

vLLM declares its command line two ways. Most flags are string literals in add_argument; the rest are generated in a loop from dataclass fields with no literal anywhere. A literals-only oracle reported --tool-call-parser, --chat-template and --enable-auto-tool-choice as non-existent. All three are real, and the oracle was calling correct answers hallucinations.

Jurisdiction was far too broad. The first version judged every --flag and every backticked identifier. Across 33 real answers that gave 106 checkable mentions at a 42% "not found" rate, and almost none were hallucinations:

An oracle that reports these as contradictions is worse than no oracle, because its verdicts carry the authority of ground truth.
What it actually wasExample

Another tool's flag, used correctlynumactl --cpunodebind

A variable from the model's own examplea_val, b_val

It now rules only on flags appearing inside an actual vLLM invocation, and does not adjudicate config keys at all. After narrowing, the same answers give 7 adjudicable claims and 0 contradictions, and every flag the answers attributed to vLLM is real. The cost is recall, and that is the right way round: a hallucinated flag outside a command line falls through to the judge, which the design already has as a fallback. A false contradiction has no safety net.

Verified in both directions — an invented --enable-turbo-mode inside a serve command returns contradicted, not merely unsupported, because the source says otherwise.

The finding that nearly became a false headline

The two failure columns are separate on purpose. A claim citing a span that does not support it asserted something its own evidence contradicts; a claim citing nothing is merely unattributable. The first version of this table folded both into one "unsupported" figure and reported 37%. Split apart, the strict failure rate is 1 claim in 496 — the 37% was almost entirely uncited claims, and publishing it as a hallucination rate would have been wrong.

A second correction in the same area: honest hedging was being scored as hallucination. Sentences like "the provided spans don't cover S3 credential configuration" assert nothing about vLLM — they are the model correctly declining, which is precisely what the abstention policy exists to encourage. Counting them as unsupported would push the system toward confident guessing. They are now excluded from the faithfulness denominator.

Verifier agreement

306 claims scored by both the free check and the paid judge

Measured on the 33-question run. The judge has not been re-run at 52 questions; an agreement rate over 306 claims is not fragile.

The two agree on 301 of 306 claims (98%) on the binary question of support. The judge was stricter on 2, similarity on 3. That number is the phase 2 argument in miniature: a free check already reproduces a paid one almost everywhere, and the question worth asking is whether the remaining 2% matters.

No claim cited a span that failed to support it. Both verifiers agree, and every one of the judge's 31 unsupported verdicts is on a claim carrying no citation at all. What the judge adds is a distinction similarity cannot make: it splits the uncited claims into genuine assertions that should have been cited and sentences that are not factual assertions about vLLM at all.

Verified on a constructed case, because the real answers contain none

Given a span reading "Default 128" and the claim "max_num_seqs defaults to 512", the judge returns contradicted with the reason "The span states the default is 128, not 512". Those strings differ by one token, so cosine similarity is high. This is the failure similarity cannot see.

Triad and the ragas cross-check

two implementations of the same three metrics, and why they disagree

The ragas column is partial: it exhausted the API budget after roughly 17 of 52 samples. The disagreement it did surface is the useful part.
MetricThis reporagasSame thing?
Faithfulness1 in 4960.94roughly agrees
Answer relevance0.980.57no
Context0.59 relevance0.88 precisiondifferent metric

The answer-relevance gap is definitional, not noise. This project's rubric states explicitly that an honest "the documentation does not cover this" is relevant — it answered the question, and penalising it rewards guessing. Ragas's AnswerRelevancy generates questions from the answer and measures their similarity to the original, so a non-answer scores near zero. Both metrics are internally consistent. They measure different things and share a name.

That is the argument for running both rather than trusting either: quoting a framework's number without its definition is how a results table ends up meaning nothing. Ragas also costs roughly 5× more per sample — about $0.13 against $0.026 — because AnswerRelevancy alone makes several generation calls per sample where the triad scores relevance and every span in one. That figure is inferred from budget consumed rather than metered per call.

Decisions that diverge from the spec

recorded in CLAUDE.md so a later session does not silently undo them

  • Claim extraction is deterministic, not model-driven. The generator already cites a span per claim, so the pairs are in the text. This keeps runs reproducible, makes re-thresholding free, and avoids letting one model both invent the claims and rule on them — which would let its segmentation choices set the denominator of the faithfulness metric.
  • The triad is implemented, and ragas runs beside it. Ragas requires LangChain, which the spec forbade while also naming ragas. Those cannot both hold. The triad was written directly; once LangChain was permitted, ragas was added as a cross-check rather than a replacement.
  • The oracle rules only on CLI flags inside a vLLM invocation and does not adjudicate config keys, for the precision reasons above.
  • CI evals run over a fixture corpus. Building the real one takes about fifteen minutes per push.

Two maintenance costs of the ragas dependency

Recorded because they will bite whoever touches it next. Ragas 0.4.3 still imports langchain_community.chat_models.vertexai, removed in langchain-community 0.4, so that is pinned below 0.4. And Opus 5 rejects temperature outright while LangChain sends one by default and ragas overwrites it per call, so both are suppressed via temperature=None and bypass_temperature.

Offering 20 requests per second yields the same 12.5, which is what saturation should look like: the server holds its latency and stops accepting more work rather than degrading. The GPU sat at 18% utilisation and 59.8 W against a 125 W limit, so at 3B the bottleneck is scheduling overhead rather than compute.

The one setting that makes vLLM run on WSL2 at all

vLLM refuses to start with RuntimeError: UVA is not available. The cause is policy, not capability: is_uva_available() reduces to is_pin_memory_available(), and vLLM disables pinned memory by default on WSL2 even on kernels past its own 4.19.121 gate. This kernel is 6.6.87.2. Setting VLLM_WSL2_ENABLE_PIN_MEMORY=1, a supported environment variable rather than a patch, makes it work.

The GPU cannot reach a pod on this machine

The k3s cluster itself works. Built via k3d with a custom CUDA node image, the node resolves the GPU and k3s auto-configures the nvidia containerd runtime. What fails is the last hop into a pod, for two independent reasons:

  • The NVIDIA device plugin cannot start. It needs NVML to enumerate devices, and NVML returns Not Supported inside a pod nested in a k3d node.
  • Manual passthrough is refused by the OS. Staging the driver libraries and mounting /dev/dxg reaches GPU access blocked by the operating system.

Both calls succeed one level up, in a plain docker run --gpus all, so these are artefacts of running Kubernetes inside Docker inside WSL2 rather than limits of the hardware. On bare-metal Linux the device plugin is the normal supported path. The manifests in deploy/k3s/ are written for that case and the cluster build is reproducible from them.

The quantization delta is not measured

The spec asks for a memory and throughput delta between quantized and unquantized. That needs the same model served both ways, and the disk filled before the 6.2 GB bf16 weights finished downloading, with 3.3 GB free. It is left unmeasured rather than estimated from the AWQ figures. Freeing about 8 GB and re-running the two commands in deploy/RESULTS.md completes it.

Guide: what remains

in the order I would do them

Deploy the demo to Hugging Face Spaces

you~30 min

Everything is built: app.py at the repo root is the Spaces entrypoint, and src/anchor/demo/app.py holds the Gradio interface. A Space has no Postgres, so the corpus must be reachable over the network.

  1. Host the corpus somewhere reachable — Neon, Supabase or Railway all offer a free Postgres with the pgvector extension.
  2. Load the corpus into it: point ANCHOR_PG_DSN at the hosted database and run anchor db init, ingest, chunk, index, oracle-build.
  3. Create a Space (Gradio SDK), push the repository to it, and set two secrets: ANCHOR_PG_DSN and ANTHROPIC_API_KEY.
  4. Add a requirements.txt for the Space — it does not read pyproject.toml.

Before you make it public

The demo calls the generation API on every question with no rate limit. A public Space with your key attached will spend real money at whatever rate visitors ask questions. Add a per-session cap, or keep the Space private and share it selectively.

File the vLLM documentation pull request

you~1 hour

Drafted in contrib/vllm-docs-pr/. The gap is real and the harness found it rather than a hunch: vLLM has five logging environment variables and no logging documentation page, which is why "How to disable logging" is one of two golden questions no configuration can answer.

The draft carries a pre-filing checklist. Work through it in order:

  1. Re-read vllm/envs.py and vllm/logger.py at current main — the draft was verified at 65f3fca5 and vLLM moves daily.
  2. Render the page in a local mkdocs serve.
  3. Confirm issue #6660 is still the best one to reference.
  4. Read vLLM's CONTRIBUTING.md for the current DCO and title conventions.

This one is worth doing properly: a merged documentation PR to a project with this much traffic is a stronger artifact than any table in this report.

Finish the golden set to 60–80

free~2 hours

Curation and the recall harness never call the generation API, so extending the set and re-running recall costs nothing. 168 unused question-shaped candidates are already harvested in data/golden/candidates.jsonl. 

uv run anchor golden propose --limit 80 --out evidence.txt
# read evidence.txt, add entries to data/golden/golden.yaml

Curate against the evidence, never the title. Two rules keep the set honest: keep questions the system fails, and drop questions no documentation can answer rather than marking them hard. Regenerating answers and grounding on the larger set does cost money — roughly $0.03 per question for answers plus about $0.026 each for the triad.

Complete the ragas comparison

~$3optional

The finding is already established and more samples cannot overturn it, so this is a decimal-tightening exercise. Run uv run anchor ragas with enough credit to finish all 52 samples. Budget roughly $0.13 per sample.

Phase 2 — LoRA judge distillation

October

The case for it is already measured, which is the unusual part: span attribution reproduces the judge on 98% of claims, and the claims table holds 802 labelled rows accumulated as a byproduct of work already done.

  1. Harvest (claim_text, supporting span, verdict) from claims where verifier = 'llm_judge'.
  2. LoRA-tune Qwen2.5-1.5B-Instruct with PEFT. Use QLoRA at 4-bit — the GPU is a 12 GB laptop part.
  3. Report Cohen's κ against the Claude judge, not raw accuracy: the classes are heavily imbalanced at roughly 194 supported to 31 unsupported.
  4. Plot agreement against cost per judgment. That is the second chart.

Be ready to defend the sample size

802 claims is thin for fine-tuning, and most carry the same verdict. Generating more judged claims first — by running the judge over a larger golden set — is probably the right first step, and it is cheap relative to the training run.

Phase 3 — finish the serving numbers

~1 hour

The serving path is built and measured. Two pieces remain, and neither needs new code.

  1. The quantization delta. Free about 8 GB, then serve Qwen/Qwen2.5-3B-Instruct in bf16 and re-run the same k6 script. Both commands are in deploy/RESULTS.md. The obvious candidate for the space is a 7.2 GB Phi-3 model sitting in the Hugging Face cache from earlier work, but that is yours to decide on.
  2. GPU scheduling under Kubernetes needs bare-metal Linux, or any Linux box with a GPU. The manifests apply unchanged; there you install the NVIDIA device plugin instead of staging driver libraries, and nvidia.com/gpu becomes an allocatable resource. That is also what makes an HPA on queue depth meaningful, since there is then more than one schedulable GPU slot to scale into.

What the resume bullet can honestly say

"Served a quantized model with vLLM at ~750 RPM and 2.74 s P99, measured with k6" is supported by this run. "On k3s" is not, on this machine: the cluster runs and the manifests are real, but the model was served by Docker because the GPU cannot reach a pod under WSL2.

Command reference

the whole pipeline, in order

# setup
cp .env.example .env          # then fill in ANTHROPIC_API_KEY
uv sync --all-extras
docker compose up -d db       # Postgres 16 + pgvector on host port 5433
